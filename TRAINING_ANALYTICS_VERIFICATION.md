# Training analytics phase 1

## Behavior

Settings stores an optional integer FTP (50–500 W) in application SharedPreferences
training_settings/ftp_watts. Blank clears it. There is no default FTP. Reads and committed
writes run on IO; failures are visible. No new library dependency.

Pure TrainingAnalytics operates on raw trainer power, never chart downsampling. Samples
are sorted/grouped by floor(elapsedMillis / 1000), within [0, saved duration). Multiple
rows in one second are averaged; any null or negative power invalidates that second.
Zero is valid. Each NP window requires 30 consecutive valid one-second buckets; missing
buckets/nulls reset it. This is stricter than the existing >3-second continuity cutoff
and cannot bridge such gaps. No zero filling, interpolation or partial-window padding.
Rides under 30 seconds or without a complete window return no NP. NP is the fourth root
of the arithmetic mean of fourth powers of all valid 30-second mean powers.

IF = NP / FTP.
TSS = elapsedSeconds * NP * IF / (FTP * 3600) * 100
    = elapsedHours * IF^2 * 100.
Duration is the saved session monotonic duration, never row count or valid-window count.
Missing sensor intervals do not shorten TSS duration. Sparse coverage can make NP/TSS
unrepresentative; the localized UI states this limitation. No NP/FTP means no IF/TSS.

## Historical correctness and migration

Room schema 2 adds only nullable ride_sessions.analyticsFtpWatts. Explicit MIGRATION_1_2
uses ALTER TABLE; old sessions/samples remain intact. No destructive fallback.
At Start ride, RoomRideRepository.start reads current FTP immediately before inserting
RideSession and stores it in analyticsFtpWatts, including null if unset. Service lifecycle,
recorder, samples and NP calculations are unchanged. Detail loading is read-only and
never consults global FTP. No additional migration or dependency.

Legacy nulls remain null: there is no reliable way to distinguish an older unknown FTP
from an intentionally unset ride-time FTP. NP remains available; IF/TSS stay unavailable.
Previously stored non-null snapshots remain unchanged, including snapshots written by the
old first-detail behavior. Their original ride-time FTP cannot be reconstructed reliably.

Regression: set 130, start/end without viewing details, set 170, then open the old ride:
it must still show 130. A new ride uses 170. A ride started unset must stay null even if
FTP is later set and details reopened. Restart the app and recheck all three rides.

## Physical checks (no APK generated by this task)

1. Update/run from Android Studio WITHOUT uninstalling. Check existing history, sample
   counts and charts survived the schema migration.
2. Leave FTP blank. Open an unanalysed ride with over 30 seconds of continuous power:
   NP should appear; IF/TSS remain No data. A short ride has no NP.
3. Settings: reject 49, 501 and decimals; accept 50–500 integers; save your actual FTP before starting a new ride.
   Restart the app and confirm it persists. Clearing leaves it unset.
4. Open an eligible ride, note saved FTP, NP, IF and TSS. Change FTP, reopen the same
   ride, restart: its FTP/IF/TSS must remain unchanged. A newly started ride uses
   the newly configured value. Do not use invented test FTP as a training recommendation.
5. Record a steady ride, including Home/locked-screen time. End and inspect metrics plus
   existing charts. Near-constant 100 W should give NP near 100 W. For arithmetic checking,
   NP=100, FTP=200, duration=1 hour gives IF=.50 and TSS=25 (ten minutes gives ~4.17).
6. Check Chinese/English settings, errors and analytics. Verify existing ERG and sensor
   behavior. Missing data must remain gaps; unavailable analytics must not appear as zero.
